# Ratchet State Persistence V1 -- implementation design proposal

**Status: DESIGN PROPOSAL - NOT FROZEN.** This document defines the proposed boundary for persisting the existing in-memory Double Ratchet state. It does not change the network protocol, ratchet KDFs, message headers, or test-vector values. The proposed format must be reviewed and frozen before implementation.

## 1. Objective and scope

Allow an Android client to restore one messaging session after process death or an ordinary interrupted write without exposing protocol secrets to Kotlin. Persist the complete state currently held by `native/crypto-core/src/double_ratchet.rs::RatchetState`, including skipped-message keys, so replay and out-of-order behavior remains correct after restart.

This is local at-rest storage, not a network object and not a portable backup format. This boundary does not implement the handshake lifecycle, message UI, HTTP API, media, push, or a multi-device synchronization protocol.

## 2. Security invariants

1. Root key, DH private key, sending/receiving chain keys, and skipped-message keys remain inside Rust. Kotlin receives only an opaque sealed record and public session metadata.
2. No message key may be reused for two distinct plaintexts. Because the message AEAD nonce is fixed to zero by the frozen protocol, this is a critical invariant.
3. Deserialization is fail-closed. A malformed, non-canonical, unsupported-version, wrong-key, wrong-session, or unauthenticated record must not produce a usable state and must not cause automatic creation of a replacement session.
4. A valid stored state must satisfy semantic invariants, including `DHS_pub == X25519(DHS_priv)`, a unique skipped-key identifier for every retained key, and no more than `MAX_SKIPPED_MESSAGE_KEYS` (currently 1,000) skipped keys.
5. Temporary plaintext/key buffers are zeroized where Rust ownership and the existing `Zeroizing` type permit. This is not a claim of perfect compiler- or platform-wide zeroization.
6. Format versioning is independent of the wire-protocol version. Unknown fields or versions are rejected; migrations must be explicit and tested.

## 3. Proposed session binding

Every stored ratchet state is bound to a public `SessionBinding` held by the native session context and checked on restore. The session-store ID is generated by Rust for each new local session, not chosen freely by the UI layer:

- local `AccountID` (16 bytes);
- local `DeviceID` (16 bytes);
- peer `AccountID` (16 bytes);
- peer `DeviceID` (16 bytes);
- local account epoch (unsigned 32-bit integer, at least 1);
- peer account epoch (unsigned 32-bit integer, at least 1);
- a local opaque session-store ID (16 bytes), generated freshly for a new local session record.

The session-store ID is local bookkeeping, not a protocol field and not a shared identifier between clients. It prevents two local snapshots for the same peer from being treated as the same storage object. Public binding values are included in the authenticated plaintext and are supplied as associated data when sealing/restoring; a mismatch must fail closed. The authenticated caller must also verify that the binding still corresponds to the current identity and currently authorized peer/device epoch before using the state.

## 4. Proposed plaintext payload

The payload is one canonical PM-CBOR-2026 map. It reuses the existing strict codec but is a local storage payload, not a network/wire contract. Exactly these integer keys are allowed:

| Key | Value | Validation |
|---:|---|---|
| 1 | format version | unsigned integer exactly `1` |
| 2 | local session-store ID | byte string, exactly 16 bytes |
| 3 | local AccountID | byte string, exactly 16 bytes |
| 4 | local DeviceID | byte string, exactly 16 bytes |
| 5 | peer AccountID | byte string, exactly 16 bytes |
| 6 | peer DeviceID | byte string, exactly 16 bytes |
| 7 | local account epoch | unsigned 32-bit integer, at least 1 |
| 8 | peer account epoch | unsigned 32-bit integer, at least 1 |
| 9 | `RK` | byte string, exactly 32 bytes |
| 10 | `DHS_priv` | byte string, exactly 32 bytes |
| 11 | `DHS_pub` | byte string, exactly 32 bytes; must match `DHS_priv` |
| 12 | `DHR_pub` | `null` or byte string exactly 32 bytes |
| 13 | `CK_s` | `null` or byte string exactly 32 bytes |
| 14 | `CK_r` | `null` or byte string exactly 32 bytes |
| 15 | `Ns` | unsigned 32-bit integer |
| 16 | `Nr` | unsigned 32-bit integer |
| 17 | `Pn` | unsigned 32-bit integer |
| 18 | skipped-message keys | array of entries described below; maximum 1,000 entries |

Each skipped-message-key entry is an array of exactly three values in this order: ratchet public key (32-byte string), sequence number (unsigned 32-bit integer), and message key (32-byte string). Entries are encoded in deterministic ascending order by `(ratchet_public, sequence_number)`. Duplicate identifiers are rejected. The decoder rejects any payload that exceeds the strict codec's 256 KiB input bound or the skipped-key count limit.

The decoder must reject missing, extra, duplicate, wrongly typed, or wrongly sized fields; non-canonical CBOR; invalid session binding; inconsistent public/private DH key material; and impossible state combinations identified by the ratchet implementation. The exact cross-field semantic checks should be implemented alongside round-trip tests rather than weakening existing ratchet logic.
The implementation must define explicit valid-state invariants for at least the responder's pre-Message-0 state, the initiator's pre-first-reply state, and normal post-handshake states. For example, `DHR_pub == null` is valid only for the responder's initial state; in that state `CK_s`, `CK_r`, and skipped keys are absent/empty and `Ns`, `Nr`, and `Pn` are zero. `CK_r == null` in an initialized initiator state requires `Nr == 0`. These examples are a starting point for reviewing every state transition, not a substitute for tests against the existing state machine.

The source-level invariant review must cover the actual reachable shapes in `native/crypto-core/src/double_ratchet.rs` and `normal_ratchet_linear.rs`, including:

- Bob's `init_bob` state: `DHR_pub`, `CK_s`, and `CK_r` are absent; `Ns = Nr = Pn = 0`; the skipped-key map is empty.
- Alice's `init_alice` state before a peer reply: `DHR_pub` and `CK_s` are present, `CK_r` is absent, and `Nr = 0`. Do not require `Ns = 0` for every pre-reply snapshot: `encrypt_message_0` advances it to 1, and subsequent outbound behavior must follow an explicit protocol rule.
- Bob after authenticated `ingest_message_0`: `DHR_pub`, `CK_s`, and `CK_r` are present; `Ns = 0`, `Nr = 1`, and `Pn = 0`; skipped keys are initially empty.
- Established normal-ratchet states, including skipped-key ordering/uniqueness and counter bounds.
- The expected `receive_first_dh_ratchet` path starts from Alice's initialized state after Message 0: the helper sets `DHR_pub` and `CK_r`, retains the existing `CK_s`, sets `Pn` to the previous `Ns`, and resets `Ns` and `Nr` to zero. **This transition guard is already implemented at review base `d10afb4bd9bc914295d4d0b349482673b434adfb`.** The source requires the Alice-side pre-first-reply shape (`DHR_pub` and `CK_s` present, `CK_r` absent, `Ns >= 1`, `Nr = Pn = 0`, and no skipped keys) and rejects a repeated peer ratchet public key. Existing Rust tests cover the valid transition, Alice/Bob rejected initial states, inconsistent shapes, unchanged state on rejection, and multiple Alice sends before the first peer reply. Do not implement this guard again; the persistence validator must preserve the same accepted/rejected lifecycle shapes.
For each accepted shape, validate derived `DHS_pub` against `DHS_priv`, range-check counters before arithmetic, reject duplicate skipped-key identifiers, and test that serialization/restore preserves the exact state semantics. These checks must be grounded in the existing state machine, not assumptions inferred from field names.

Secret-memory requirement: the current generic PM-CBOR path is not yet suitable for secret-state serialization without a dedicated zeroization audit. `Value::Bytes(Vec<u8>)` and decoded byte strings do not zeroize on drop. The current map encoder also creates plain scratch buffers (`kb`, `vb`, and `enc` entries) which can contain copies of secret fields and are dropped without zeroization. Wrapping only the final plaintext or encoded output buffer is insufficient. Before implementation, either add an explicitly secret-aware codec path that uses RAII zeroization for every secret-bearing intermediate on success, error, and unwind, or implement a dedicated ratchet-state encoder/decoder with that property. Do not pass ratchet secrets through the generic `Value::Bytes` encode/decode path until the intermediate-copy behavior is addressed and reviewed.

## 5. Proposed sealed-record envelope

The sealed record format is:

1. 9-byte header: ASCII `PMDRSTOR` followed by version byte `0x01`;
2. 12-byte nonce generated afresh by the OS CSPRNG for every save;
3. ChaCha20-Poly1305 ciphertext of the canonical plaintext payload plus the 16-byte authentication tag.

The exact associated data is the 9-byte header followed by the session-store ID (16 bytes), local AccountID (16), local DeviceID (16), peer AccountID (16), peer DeviceID (16), local epoch (`uint32_be`), and peer epoch (`uint32_be`). The session binding is checked again against the decrypted payload after authentication.
Use a fresh random 32-byte ratchet-state data-encryption key (DEK) for each local session. It must be distinct from the identity-record Storage DEK and every protocol key. On Android, wrap this per-session DEK with a dedicated Android Keystore AES-GCM key using a ratchet-only alias that is separate from the identity-storage alias. Persist the wrapped ratchet DEK, session binding, and sealed ratchet record together in the same durable local store and transaction; never persist the raw DEK. On restore, unwrap the DEK only into memory, authenticate/decrypt the record, re-check the binding, and clear temporary key buffers. A missing Keystore key, failed unwrap, or ambiguous record must fail closed and must never trigger automatic session replacement. Key rotation and migration need explicit tests.
### Wrapped ratchet-state DEK record (V1)

Use the dedicated Android Keystore AES-GCM wrapping key, with alias `pm_ratchet_state_wrap_v1` mapped to wrapping-format version `0x01`. The alias is separate from the identity-storage alias. Configure the Keystore key for AES-GCM encryption/decryption with a 128-bit authentication tag and randomized encryption; do not export or persist the wrapping key.

The serialized wrapped-DEK record is exactly 69 bytes:

1. 9-byte header: the 8 ASCII bytes `PMRDEKWR` followed by version byte `0x01`;
2. 12-byte fresh nonce/IV generated by Android Keystore for each wrap operation;
3. 48-byte AES-256-GCM output for a 32-byte ratchet-state DEK: 32-byte ciphertext followed by the 16-byte authentication tag.

Construct `AAD_wrap` as the exact concatenation below, with no separators:

`header (9) || session_store_id (16) || local_AccountID (16) || local_DeviceID (16) || peer_AccountID (16) || peer_DeviceID (16) || local_epoch (uint32_be) || peer_epoch (uint32_be)`

The AAD is 97 bytes. Before authentication, treat the header/version byte as untrusted. Use it only to select a supported version from a strict allowlist that maps each version to its exact wire layout and Android Keystore alias; do not try arbitrary or fallback aliases, and do not infer the version from UI metadata. Rebuild AAD from the expected native session binding, never from stored or UI-supplied binding fields. Authenticate the record using that AAD and the stored nonce/ciphertext/tag before trusting any record metadata. After GCM verification succeeds, validate that the authenticated header/version maps to the alias used and verify the stored binding against the expected native binding. An unknown version or missing alias must fail closed. Never reuse a GCM nonce with the same wrapping key. A nonce/tag/length/version mismatch, wrong binding, missing alias, authentication failure, or ambiguous record must fail closed; do not generate a replacement DEK or ratchet session automatically.

Store the wrapped-DEK record, its binding/version metadata, and the sealed ratchet-state record in the same durable local transaction. Never persist the raw ratchet-state DEK. The DEK may cross UniFFI only as the narrowly scoped 32-byte local-at-rest key needed for wrapping/unwrapping and ratchet-record seal/restore; update `docs/phase0/07-uniffi-interface.md` before implementation. Do not expose it to general UI code, logs, crash reports, strings, analytics, or persistent plaintext storage. Clear temporary buffers on both Kotlin and Rust sides as far as the platform/runtime permits, and document unavoidable copies.

For rotation, retain the old versioned Keystore alias until all records using it have been migrated. Unwrap and rewrap the same per-session DEK with a fresh nonce and the new versioned alias, then atomically commit the new wrapped-DEK record and version metadata. Do not delete or replace the old alias until migration verification is complete. A migration failure must preserve a usable prior record; test interrupted and partially completed migrations.

The existing `AccountContext.seal_for_storage` API is specifically documented for the identity-at-rest record. Do not reuse that identity DEK for ratchet state. If the ratchet-state DEK crosses UniFFI, update `docs/phase0/07-uniffi-interface.md` to record this narrowly scoped exception, the permitted seal/restore operations, and zeroization limitations before implementation. Raw ratchet keys, chain keys, and message keys must never cross the FFI boundary.

Restore failures should map to a generic public storage/invalid-record error; diagnostics must not expose plaintext, root/chain keys, message keys, or other secret-bearing material.

## 6. Atomic message-processing requirement

**State serialization alone is not sufficient to enable app messaging.** The application must not mutate its only live state and then attempt a best-effort save.
The current ratchet functions mutate `RatchetState` in place, and the state is not currently `Clone`. The implementation therefore needs a controlled candidate-state mechanism with deep-copied secret fields that remain zeroizing, or an equivalent native transaction API. Do not mutate the only live state and try to roll it back after a failed database commit. Promote the candidate to active state only after the durable transaction succeeds.

The entire per-session operation must be serialized from candidate creation through durable commit and promotion. Two concurrent operations must never derive candidates from the same active snapshot and both commit. Enforce this with a native per-session mutex/actor or an equivalent transaction/generation check. Test simultaneous outbound operations and simultaneous inbound duplicates.

### Outbound message-key use and crash recovery (critical requirement; exact staging format NOT FROZEN)

The frozen Double Ratchet boundary uses the fixed all-zero AEAD nonce and states that each derived `K_msg` is single-use. The current `encrypt_message` and `encrypt_message_0` paths derive a message key and produce ciphertext before the new state is durably committed. Therefore, candidate-state plus outbox atomicity alone does not resolve the crash window: if encryption has run but the durable transaction has not committed, a restart can restore the prior chain state. The next outbound attempt must not encrypt a different plaintext/header/AAD tuple from that old state, because it would reuse the same `K_msg` with the same nonce.

V1 must define a durable outbound-attempt lifecycle before implementation:

- Before the first outbound AEAD invocation, atomically persist an authenticated `ARMED` attempt marker bound to the session ID, current `record_generation`, a fresh operation ID, and a fixed envelope ID / finalized message context. Include the marker in the authenticated per-session entry and account/device index; increment `account_index_generation` using the existing account-wide CAS rule. Only one armed outbound attempt is permitted per session, and no other ratchet operation may proceed while it is unresolved.
- Invoke outbound encryption at most once for that armed attempt. If the database commit fails while the exact candidate and ciphertext remain in memory, retry only persistence using those exact bytes and that exact candidate; never call AEAD again as a transaction-retry strategy. Do not publish or send the staged ciphertext.
- Once execution crosses the native boundary immediately before the outbound AEAD invocation, conservatively treat that message key as consumed even if AEAD returns an error, the operation panics/unwinds, or no ciphertext reaches the caller. Keep the ARMED attempt unresolved and fail-stop/quarantine the session unless the exact ciphertext and matching candidate state can be durably staged. Never clear the marker or invoke AEAD again from the same source state/key after an uncertain invocation. A disarm/abort is permitted only when the native operation can unambiguously prove that it exited before AEAD was invoked; do not infer this from a generic error category. Fault-inject errors and panics immediately before, during, and after the AEAD call.
- The staging record, its exact digest/status in the per-session entry, entry MAC/commitment, updated account/device index and index MAC must be written in one atomic durable transaction. Increment `account_index_generation` according to the existing CAS rule; do not advance `record_generation` for a stage-only metadata change, but do advance it exactly once when the staged candidate becomes the committed ratchet state. A staging record without the matching entry commitment in the latest authenticated index, or an entry that claims staging without the exact matching staged bytes, is not resumable and must fail closed/quarantine. A crash before this atomic staging transaction commits leaves only ARMED and is handled by the conservative quarantine rule above.
- Define an authenticated, encrypted-at-rest staging record that can hold the exact ciphertext/envelope data and sealed candidate state, bound to the operation ID, session binding, and source generation. Commit the staging record before treating recovery as resumable, and bind its exact digest/status into the authenticated catalog entry. After process restart, if a valid staging record exists, finalize the state/outbox/catalog transaction from that staged candidate without re-encrypting.
- If the process dies after the attempt is armed but before a valid staged candidate/ciphertext is durably recorded, the old state must be fail-stopped/quarantined. Do not encrypt again from that old state, silently clear the marker, or auto-create a replacement session. Require an explicit new authenticated session-establishment path before outbound messaging resumes. This conservative recovery may lose the pending message and reduce availability, but it preserves the frozen single-use message-key rule.
- The final commit must atomically activate the candidate state, commit the outbox ciphertext and delivery metadata, advance `record_generation` once, update the per-session entry/commitment and account index/MAC, and clear the armed/staged marker. If commit succeeds but native promotion fails, restore from that committed record before publishing the result. Network send occurs only after the final commit and promotion.

### Proposed outbound staging record format V1 (DESIGN ONLY; NOT FROZEN)

Use a dedicated staging key derived inside Rust; the staging key never crosses UniFFI and the Android Keystore catalog-MAC key is not reused for encryption. Derive `K_stage` as `HKDF-SHA-256(salt = session_store_id (16 bytes), IKM = ratchet_state_DEK (32 bytes), info = ASCII("PM-DR-STAGING-KEY-V1"), L = 32)`. This is a per-session, domain-separated key for local crash-recovery staging, not a protocol key. Clear the DEK input copy, derived key, plaintext staging buffer, and intermediate buffers on all controlled success/error paths; do not claim perfect managed-runtime zeroization.

The outer staging record is binary-framed, not a PM-CBOR map containing one oversized state-record byte string. Its exact V1 layout is: 9-byte header (`ASCII("PMDRSTAG") || 0x01`); 12-byte fresh OS-CSPRNG nonce; then ChaCha20-Poly1305 ciphertext including the 16-byte tag. Generate the nonce once for each staging-record creation. A persistence retry must write the exact already-created staging bytes; it must not re-encrypt or regenerate the stage record. Any newly created stage record uses a fresh nonce.

The authenticated staging plaintext uses fixed-width big-endian lengths and exact binary segments in this order: payload version (1 byte, `0x01`); operation kind (1 byte, `0x01` for outbound); operation ID (16 bytes); session-store ID (16 bytes); source `record_generation` (uint64_be); envelope length (uint32_be); sealed candidate-state record length (uint32_be); exact serialized outbound envelope bytes; exact sealed candidate-state record bytes. The fixed prefix is 50 bytes before the two variable-length segments. Reject unknown versions/kinds, zero or invalid IDs, overflow, zero/over-limit lengths, trailing bytes, truncation, and any decoded value that disagrees with the authenticated ARMED/catalog metadata. In particular, the staged envelope ID, operation ID, session ID, and source generation must match the ARMED marker and expected native session context.

The exact AAD is 122 bytes: `header (9) || session_store_id (16) || operation_id (16) || local_AccountID (16) || local_DeviceID (16) || peer_AccountID (16) || peer_DeviceID (16) || local_epoch (uint32_be) || peer_epoch (uint32_be) || source_record_generation (uint64_be) || operation_kind (1 byte)`. Build it only from the expected native session binding and authenticated ARMED marker. After decryption, compare every repeated payload field to the AAD/marker values. If any comparison fails, reject and quarantine the session; never repair metadata from the staged record.

The stage record contains the exact sealed candidate-state record and exact outbound envelope, both covered by the outer AEAD. The candidate-state record uses the ratchet-state seal format and its own fresh nonce; the outer staging record uses the independently derived `K_stage` and a separate fresh nonce. Do not place the complete sealed-state record in a single PM-CBOR `bstr`, because `MAX_BSTR` (65,552 bytes) is smaller than a maximum permitted sealed ratchet-state record. The normal final state and outbox records must be byte-for-byte copied from this authenticated stage during finalization; finalization must not invoke outbound AEAD or re-encrypt the message.

Proposed hard cap: `MAX_OUTBOUND_STAGE_RECORD_V1 = 384 * 1024` bytes including header, nonce, and tag. This is a proposal, not accepted until tests prove it covers the largest supported sealed candidate-state record plus the maximum legal serialized envelope and framing overhead. Reject the length before allocating the full record/plaintext. If exact worst-case calculations or tests exceed the cap, revise the cap before freezing; do not truncate content or raise the cap silently. Keep the 256 KiB PM-CBOR limit for the canonical ratchet-state payload itself; the binary staging wrapper has its own explicit bound.

The staging catalog status must be one of `ARMED` or `STAGED` with exact schema-defined fields. `ARMED` binds operation ID, envelope ID/finalized native message context, source `record_generation`, and current account-index generation, and is durably authenticated before any outbound AEAD invocation. `STAGED` additionally binds the SHA-256 digest of the exact outer stage bytes. The stage bytes, `STAGED` entry and MAC/commitment, and updated account/device index and MAC must commit atomically. A stage record without this matching current authenticated catalog commitment is not resumable. Stage-only transitions increment `account_index_generation` but not the active ratchet `record_generation`; promoting the candidate during finalization increments `record_generation` exactly once and clears the staged status in the same final transaction.
### Active versus staged state-record digest semantics (V1 design requirement; NOT FROZEN)

The per-session entry's `state_record_digest` always identifies the last committed active-state record. During `ARMED` and `STAGED`, do not repoint it to the candidate state. `source_record_generation` in the attempt marker must equal the active state's current `record_generation`. The `STAGED` status additionally authenticates the exact outer staging-record digest. The candidate sealed-state record is carried inside that encrypted staging record; it is not the active record merely because it has been durably staged.

On finalization, authenticate and decode the staged record, validate its operation/session binding and source generation, verify the embedded candidate-state record and all RatchetState invariants, and then in one database transaction copy the exact embedded candidate-state bytes into the active-state record slot, set `state_record_digest` to the digest of those exact bytes, increment `record_generation` exactly once, commit the exact staged envelope to the outbox, clear the `ARMED`/`STAGED` status, and update the entry commitment plus account/device index and MAC. Do not rerun ratchet encryption or silently reseal/re-encrypt the message during finalization. If the implementation needs to reseal the candidate-state record, that must be a separately specified and tested operation that cannot repeat message AEAD or change the staged envelope.

### Ambiguous durable-commit outcome (V1 recovery requirement; NOT FROZEN)

A database call that reports an error, loses its acknowledgement, or is interrupted must not automatically be interpreted as proof that the transaction did not commit. Before retrying, resolve the operation by re-reading the bounded persisted records and verifying the current account-index MAC, per-session entry MAC/commitment, generations, status, and exact record digests. If the exact operation is already committed, resume from that committed state. If the authenticated catalog still proves the prior `ARMED` state and no staging transaction committed, an in-memory retry may write only the exact previously created staging bytes and candidate; it must not recreate staging bytes or invoke message AEAD again. If the durable outcome cannot be established, quarantine/fail-stop the session. Fault-inject a lost commit acknowledgement both when the transaction committed and when it did not, and prove recovery chooses the correct branch without duplicate state advancement or message-key reuse.
### Durable outbound operation receipt and final-commit idempotency (V1 requirement; NOT FROZEN)

The finalization transaction must durably preserve authenticated evidence that identifies the exact outbound operation after its `ARMED`/`STAGED` status is cleared. At minimum, the durable outbox row must carry the operation ID and envelope ID under a uniqueness constraint, and recovery must be able to compare the exact envelope digest, source `record_generation`, resulting `record_generation`, and resulting active `state_record_digest`. If outbox rows can be removed before every possible retry or lost-acknowledgement window has ended, retain a separate bounded completion receipt keyed by `(session_id, operation_id)` instead; its authenticated fields must bind the envelope ID and digest plus the source and resulting generations and resulting active-state digest. The receipt or outbox evidence must be committed atomically with active-state promotion, outbox insertion, staged-status clearing, and the corresponding entry/index authentication updates.

On an ambiguous final-commit result, recovery must find exactly one authenticated completion record for the operation and verify it against the active catalog/state and exact outbox envelope before reporting success. A matching operation ID with a different envelope digest, generation, or state digest is a security failure, not a retry opportunity. If no matching completion evidence exists and the database outcome cannot be conclusively shown not to have committed, fail-stop/quarantine rather than invoking message AEAD again. Define receipt retention and garbage-collection rules so an operation cannot become ambiguous merely because its idempotency evidence was deleted too early. Add fault-injection tests for lost acknowledgements after the final transaction commits, before native promotion, and after outbox delivery/cleanup; prove that retrying the same operation ID never creates a second envelope or advances state twice.

### Authentication and retention of completion evidence (V1 requirement; NOT FROZEN)

Completion evidence must be cryptographically authenticated, not trusted merely because it exists in a database row or satisfies a uniqueness constraint. Define a canonical completion-receipt encoding and a domain-separated HMAC-SHA-256 value using the specified catalog-authentication key/version. Bind at least the session ID, operation ID, envelope ID, exact envelope digest, source and resulting record generations, resulting active-state digest, immutable session-binding digest, and applicable account/device epochs. The per-session authenticated catalog entry/commitment must bind the exact receipt digest or a precisely specified authenticated receipt-set digest and sequence. The final transaction must atomically update that binding with active-state promotion, outbox insertion, staged-status clearing, and account-index authentication. Reject duplicate, missing, mismatched, stale, or unverifiable receipt evidence; a database uniqueness constraint is defense in depth, not cryptographic authentication.

Define a retention state machine before implementation. Completion evidence must remain available and authenticated until recovery has confirmed the committed operation, native promotion has succeeded, and the outbox has reached a state where cleanup cannot erase evidence still needed to resolve an ambiguous result. Outbox cleanup must atomically update any catalog-bound receipt/receipt-set metadata. If receipts are retained only for a bounded retry window, specify and enforce that window and prove no caller or restart recovery can retry an operation after its evidence expires; otherwise retain a bounded, authenticated deduplication record for the required lifetime. On restart, reconcile committed outbox/receipt state before allowing delivery, cleanup, or another operation for that session. Add tampering, deletion, stale-receipt, duplicate-operation, receipt-GC, and crash-between-commit-and-native-promotion tests.
### Maximum staging-size proof (V1 bound validation; NOT FROZEN)

The proposed 384 KiB stage cap is not accepted by calculation alone. Add a deterministic size-bound test using the largest legal `RatchetState` (including the maximum skipped-key count), the largest legal outbound envelope constructed through the actual validated `NormalMessageHeader` or `PrekeyHandshakeHeader` path, and the exact staging framing. Prove the result is at most `MAX_OUTBOUND_STAGE_RECORD_V1`; separately reject cap-plus-one before proportional allocation. Do not estimate the maximum by combining arbitrary `MAX_BSTR` fields that could never pass the actual message-header/state validators, and do not rely on an unvalidated oversized header as a legal outbound message.

Required bounds/fault tests: maximum legal envelope plus maximum legal state must fit below the proposed cap; cap plus one byte is rejected before large allocation; truncation/trailing bytes and every length boundary fail closed; wrong DEK/session/AAD/nonce/tag fails; duplicate or stale operation IDs fail; staged bytes copied between sessions fail; persistence retries preserve byte-identical stage records; a staged restore produces exactly the stored envelope/state without a second outbound AEAD invocation. Also verify the existing PM-CBOR per-byte-string bound is never bypassed by embedding an oversized state record as one `bstr`.

The exact production storage schema, error-category mapping, and recovery UX remain open. This proposed format must be reconciled with the shared account-index transaction and catalog-key rotation model and independently reviewed before freeze. Do not relax the frozen single-use-key requirement by permitting a different plaintext to be encrypted under the same chain key after a failed transaction. Do not assume deterministic re-encryption is permitted merely because identical inputs may yield identical ciphertext; that exception would require explicit protocol/security review and a documented change to the single-use invariant.

Required fault-injection points: before ARMED commit; after ARMED commit but before AEAD; after AEAD but before staging commit; after staging commit but before final commit; after final commit but before in-memory promotion; and during each corresponding restart/recovery path. Tests must prove that an unresolved armed attempt cannot reuse its old message key, a valid staged attempt is finalized without another AEAD invocation, no ciphertext is published before commit, and every failure is fail-closed.
### Proposed native session/transaction API boundary (design only; names/signatures NOT FROZEN)

The future FFI boundary needs one opaque native `RatchetSession` owner. It owns the active `RatchetState`, immutable `SessionBinding`, an operation generation, and at most one pending candidate. This is a proposed boundary, not an existing API: the current UniFFI surface exposes identity and recovery contexts but no ratchet-session handle or message operations.

- **Create or restore a session:** create a session handle only from a native-validated session-establishment path. On restore, resolve the expected binding from a trusted native session context/registry bound to the restored account identity and validated peer session; do not treat caller-supplied or database-loaded peer IDs, epochs, or session-store IDs as authoritative merely because Kotlin supplied them. The exact owner of this trusted binding and its restart lifecycle must be resolved before signatures are frozen.
- **Prepare an operation:** outbound encryption or inbound decryption operates on a secure deep candidate copy; it must not mutate the active state. The candidate stays inside Rust. Return only the application-level operation result and an opaque pending-operation handle, never `RatchetState`, serialized plaintext state, root/chain keys, skipped keys, or message keys. Keep candidate secret fields zeroizing, including temporary copies.
- **Seal the candidate:** expose a dedicated operation on the pending handle that accepts the 32-byte ratchet-state DEK and returns only the sealed candidate-state record. Build its AAD from the native session binding. Do not provide a general-purpose API that accepts arbitrary plaintext and a DEK. This is the proposed narrow DEK crossing described in `docs/phase0/07-uniffi-interface.md`.
- **Commit or abort:** after the caller's durable transaction succeeds, commit the matching pending handle/generation and promote the candidate to active state. If the transaction fails, abort and discard the candidate. Reject stale, reused, cross-session, or invalid pending handles. Allow at most one pending operation per session; concurrent operations must receive a defined busy/conflict result or use a generation check, never derive two committable candidates from the same active snapshot.
- **Application transaction:** the caller must atomically persist the sealed candidate state with the outbound envelope/outbox record, or with the inbound protected inbox item and unique deduplication marker. Network send/acknowledgement and committed-message UI state occur only after durable commit and candidate promotion. If durable commit succeeded but in-process promotion fails, fail-stop that session and reload from the just-committed record; never continue from stale in-memory state.
- **Restore:** the native restore operation authenticates the sealed record using the DEK and expected native binding, decodes with the secret-aware codec, validates all state invariants, and publishes the restored state only after every check succeeds. Any failure is fail-closed and must not create a replacement session automatically.

Crash rule: after process death, the durable transaction is authoritative. A crash before the transaction commits must recover the prior state; a crash after commit must restore the committed candidate state. The pending in-memory candidate is never itself durable authority.

Before freezing this API boundary, resolve and test the trusted binding source, opaque-handle lifecycle across restart, stable error categories, result-publication gates, and exact operation method signatures.

### Authenticated session catalog and restore binding (design requirement; exact storage primitive NOT FROZEN)

The local AccountID and DeviceID used for restore must be derived from the successfully restored native AccountContext, not supplied by Kotlin. The session-store ID must be generated by Rust with the OS CSPRNG and associated with the session at the authenticated establishment boundary. Peer AccountID, peer DeviceID, and local/peer epochs must come from the validated handshake/session-establishment result; they must not become authoritative simply because they are present in a database row.

#### Proposed Android V1 catalog authentication (NOT FROZEN)

Protect catalog metadata with a dedicated Android Keystore HMAC-SHA-256 key under versioned alias `pm_ratchet_catalog_mac_v1`. This alias must be separate from both the identity-storage key and ratchet-state AES-GCM wrapping key. Generate the MAC key in Android Keystore; do not export or persist its raw key. This is integrity protection for local metadata, not encryption and not anti-rollback protection. Confirm HmacSHA256 support on every supported Android/API/device configuration; do not claim hardware backing unless runtime/device evidence supports that claim.

Use two authenticated layers so a valid row from another session cannot silently replace the selected session. Encode payloads as strict canonical PM-CBOR-2026 bytes. Keep the following version fields distinct: `catalog_schema_version`, `entry_schema_version`, `catalog_mac_key_version`, `wrapped_dek_format_version`, and `ratchet_state_record_version`; do not overload a schema version as a cryptographic-key selector. Each catalog object uses a bounded framing of one `catalog_mac_key_version` byte, the exact canonical payload bytes, and a separate 32-byte HMAC. For V1, version byte `0x01` maps only to alias `pm_ratchet_catalog_mac_v1`. Before authentication, the version byte is untrusted and may only select one exact alias from a strict allowlist; never try fallback aliases. Compute the entry MAC as `HMAC-SHA-256(K_catalog[v], ASCII("PM-RATCHET-CATALOG-ENTRY-MAC-V1") || version_byte || canonical_entry_payload_bytes)` and the account-index MAC as `HMAC-SHA-256(K_catalog[v], ASCII("PM-RATCHET-CATALOG-INDEX-MAC-V1") || version_byte || canonical_index_payload_bytes)`. The domain separators are exact ASCII bytes with no added delimiter; `version_byte` is exactly one byte and is included in the MAC input. Verify the MAC over the original byte sequence before trusting payload metadata, then strict-decode and validate the canonical schema, requiring the authenticated payload `catalog_mac_key_version` to equal the framing version byte, and independently checking `catalog_schema_version` and `entry_schema_version` against their supported schema versions. Reject unknown key/schema versions, invalid MACs, and non-canonical payloads. Preserve exact payload bytes; do not decode and re-encode before MAC verification.

The authenticated per-session entry must bind, at minimum: schema/key version; session-store ID; local AccountID and DeviceID; peer AccountID and DeviceID; local and peer epochs; a monotonically increasing per-session record generation; and SHA-256 digests of the exact sealed ratchet-state record and wrapped-DEK record. The MAC covers every field, including both record digests. Rust generates the session-store ID; it is not caller-selected.

The authenticated account/device index must bind the local AccountID and DeviceID plus a deterministically sorted list of entries, each containing: the session-store ID; a SHA-256 digest of that session's immutable canonical binding (session-store ID, local/peer AccountIDs and DeviceIDs, and local/peer epochs); the latest `record_generation` as an unsigned 64-bit integer; and an `entry_commitment`. Define `entry_commitment` exactly as `SHA-256(ASCII("PM-RATCHET-CATALOG-ENTRY-COMMITMENT-V1") || entry_catalog_mac_key_version_byte || uint32_be(payload_length) || exact_canonical_entry_payload_bytes || entry_mac_32)`, where `payload_length` is the byte length of the canonical entry payload, encoded as an unsigned 32-bit big-endian integer, and `entry_mac_32` is the 32-byte MAC over the exact entry version byte followed by that payload. Reject lengths outside the strict catalog-entry bound. Here `entry_catalog_mac_key_version_byte` is exactly the single-byte `catalog_mac_key_version` framing field on that per-session entry; it is not `entry_schema_version`. The entry MAC and commitment both use the exact same entry framing version byte. This commitment binds the current entry version byte, generation, and exact entry-plus-MAC bytes, not only the immutable session identity.

Protect the account/device index with its domain-separated HMAC. Because the index now anchors the current per-session entry, generation, and record digests, update the account/device index and its MAC on EVERY successful ratchet-state transaction, not only on session creation/removal or immutable-binding changes. In one durable transaction, increment `record_generation` exactly once; write the new sealed state and wrapped-DEK record (if the latter changed); write the canonical per-session entry and its MAC; write the canonical account/device index and its MAC; and commit the corresponding inbox/outbox/deduplication change. Use the per-session serializer and a database generation/compare-and-swap check; reject stale candidates and generation overflow. If any operation fails, none of these records may commit. This adds index-write amplification and possible contention on every message-state update; treat that as an explicit V1 tradeoff, or design and review a different freshness anchor before freezing.
Account-wide concurrency requirement: because every message transaction updates the shared account/device index, per-session serialization alone is insufficient. Add an authenticated `account_index_generation` field to the index payload, separate from each session's `record_generation`. Increment it exactly once for every successful index update, including every successful message-state transaction. Use a database-level serialized writer or compare-and-swap against the observed `account_index_generation`, and verify that the session's own `record_generation` is still current in the same transaction. The index payload and MAC, selected entry and MAC, sealed state, wrapped DEK if changed, and inbox/outbox/deduplication mutation must commit atomically. Never replace the index from a stale snapshot or lose entries committed by another session.

If the account-index generation changed because another session committed first, rebuild the index update from the latest authenticated index while preserving that other session's committed entries. Reuse the already prepared candidate and ciphertext only if the current session generation still matches and the database confirms that none of this candidate's writes committed; do not rerun encryption from the same active state as a way to retry a failed candidate. If these conditions cannot be established, abort the candidate and fail closed for that operation. For a same-session generation conflict, reject the stale candidate and prepare a new operation only under the defined state/key-use recovery rule.

Add a cross-session concurrency test: two distinct sessions under the same account/device attempt state updates concurrently. Verify the final index contains both updates, the account-index generation advances without lost increments, each per-session generation advances exactly once, and a stale writer cannot overwrite a newer index. Also test index-generation overflow and transaction conflict/failure with no partial state, index, inbox/outbox, or acknowledgement changes.
Proposed V1 catalog bounds: cap the authenticated account/device index at `MAX_CATALOG_SESSIONS_V1 = 1024` entries and reject a new session before exceeding the cap. Require the exact canonical index payload to remain within PM-CBOR-2026's 256 KiB whole-input limit, with the 1,024-entry worst case demonstrated by a test. Reject oversized input before allocating a proportional decoded structure; do not truncate, partially load, or silently omit entries. Treat the 1,024-session cap as a proposal to validate against product needs before freezing.

With the current index retained, replaying an older valid per-session entry together with its old sealed state and wrapped DEK must fail because its generation/entry commitment does not match the index. This is protection against selective record rollback only when the latest index remains current; it is not anti-rollback protection if an attacker can also restore a mutually consistent older index and its corresponding records.

On restore, get local AccountID/DeviceID from the successfully restored native `AccountContext`. Treat the requested session-store ID as a selector only. Verify the account/device index MAC and its local identity binding first, and require the requested session-store ID to be present. Then verify the selected per-session entry MAC, compare its authenticated binding digest with the corresponding index entry, and compare its local identity to `AccountContext`. Only after these checks may the native layer use the authenticated peer identity and epochs to construct wrapped-DEK and ratchet-state AAD. Verify both record digests against the exact stored bytes before unwrap/decryption, then validate the decrypted RatchetState invariants. A row copied from another session, an index entry removed/reordered/substituted, or a record swapped independently of its catalog entry must fail closed.
Current-epoch freshness remains an unresolved requirement and must be grounded in the repository's account/device lifecycle, not inferred from this catalog. The frozen lifecycle document (`docs/phase0/08-device-lifecycle.md`) defines account epochs and says a recovery epoch becomes authoritative only after its authorization checks and 48-hour timelock; the frozen KT V1 spec (`docs/phase0/10-key-transparency-v1-frozen.md`) includes account epoch in the current identity leaf and requires client high-water/consistency handling, but explicitly does not prove account-level authorization of a device. Treat these as separate checks: verify the authorized account-epoch transition under the lifecycle rules, and use a verified current-state KT leaf/proof and accepted STH/high-water state to detect stale or conflicting published device state. KT evidence alone is not an account-authorization proof, and the catalog HMAC alone does not establish that an epoch is still current.

The current Rust `AccountContext` carries AccountID and DeviceID but no epoch or verified lifecycle status. Before freezing, define a native-owned opaque verified account-state/context (or equivalent narrow lifecycle result) that exposes the authenticated local epoch and relevant authorization/revocation status only after the lifecycle evidence is validated; never accept a raw Kotlin-supplied epoch or a caller-supplied `verified=true` flag as authority. Define how peer epoch transitions and revocation invalidate, suspend, or replace sessions, and bind the session's immutable local/peer epochs to the verified establishment result.

Offline policy must be explicit and bounded by the frozen KT client policy: a cached, previously accepted state can support only the existing documented DEGRADED/cached-state behavior, not a claim that no newer remote epoch exists. If cached transparency/account-state evidence is absent, internally inconsistent, known stale/rolled back, or in SECURITY FAILURE, fail closed for the affected session. A newly observed authorized epoch transition or revocation must prevent continued use of sessions bound to the superseded epoch according to the lifecycle rules. The proposed local catalog and its HMAC cannot independently establish online freshness or resist a full-snapshot rollback; preserve that non-claim until a separate anti-rollback mechanism is designed.

Trust boundary: the HMAC verifier is a dedicated internal Android persistence adapter using Android Keystore. This detects database tampering/substitution; it does not defend against arbitrary code executing inside a compromised app process that can bypass the adapter and call exposed application APIs. Do not expose raw binding overrides or restore primitives to UI code, and do not use a caller-supplied `verified=true` flag as proof. Rust must still compare the supplied local AccountID/DeviceID with `AccountContext` and compare all binding fields with the decrypted, authenticated state payload. If the threat model includes hostile calls from a compromised Kotlin process, this HMAC-only adapter split is insufficient: stop before freezing and design a native-verifiable trust anchor instead. Record this trust assumption explicitly.

Commit the per-session entry/MAC, sealed ratchet-state record, wrapped-DEK record, generation metadata, and associated inbox/outbox update in the same durable transaction. Update the account/device index and its MAC in the same durable transaction for every transaction that changes authenticated catalog state, including every successful ratchet-state/message update, ARMED/STAGED status transition, completion-receipt insertion or retention/garbage-collection update, and session creation, removal, or binding change. Increment account_index_generation exactly once for each successful index update. Stage-only metadata transitions do not advance record_generation; candidate activation advances record_generation exactly once. Entry/receipt authentication and account-index authentication must remain atomic under the same database compare-and-swap or serialized-writer transaction. The MAC key must never cross UniFFI. If the catalog MAC key is missing or invalid while any persisted session/catalog data exists, fail closed and never regenerate a key or re-MAC existing entries automatically. First-time key creation is permitted only during explicit clean initialization when no prior catalog/session data exists. Rotation must keep the old alias until the account index and every dependent entry are migrated and verified.

The session catalog remains subject to full-snapshot rollback: an older, internally consistent index, entry, wrapped DEK, and sealed state can still have valid MACs. Record generations help reject stale concurrent updates in the live database but are not cryptographic anti-rollback counters. The catalog storage schema, MAC-key lifecycle, and rotation policy remain proposals until reviewed against Android storage/backup behavior. Missing, inconsistent, unauthenticated, or ambiguous catalog data must fail closed; do not guess the peer/session or create a replacement.

An in-memory RatchetSession handle and any pending-operation handle are process-local capabilities, not durable identifiers. After process restart, handles are invalid and must never be reconstructed from integer/pointer values saved by Kotlin. Restore must create a new native handle only after AccountContext, catalog binding, wrapped DEK, sealed record, and RatchetState invariants all validate. Pending operations from the previous process do not survive; the durable database transaction determines whether the prior or candidate state is restored. Reject stale, reused, cross-session, and closed handles with stable, non-secret-bearing error categories.

### Pending-result publication gate (design requirement; exact method names NOT FROZEN)

Preparation and durable commit are separate states. The API contract must distinguish a staged result needed to construct the local database transaction from a committed result that may be published. An outbound ciphertext/envelope must not be sent until the state/outbox transaction commits and native candidate promotion succeeds. An inbound plaintext/result must not be shown as committed or acknowledged until the protected inbox/deduplication/state transaction commits and native candidate promotion succeeds. If plaintext must cross into Kotlin to form the protected inbox item, treat it as provisional, keep it out of UI/notification/analytics paths, and discard it on abort; specify and test this requirement explicitly.

If the database transaction commits but native promotion fails, the session must be fail-stopped and restored from the committed record before any staged result is published. Publication and delivery acknowledgement must be idempotent across retry/restart so that restoring a committed outbox item cannot cause a second state advance or ambiguous resend. These are contract requirements; do not freeze method names until the pending-result lifecycle is specified.

Add tests that swap or substitute catalog rows between two sessions, alter peer/session/epoch bindings, restore under a different AccountContext, restart with stale pending handles, abort an inbound candidate without displaying it, and recover after database commit but before in-memory promotion. These tests do not establish protection against full device rollback; that remains the separate unresolved threat-model decision.

- **Outbound:** generate ciphertext and the next ratchet state using a candidate state. Commit the candidate state and the outbound envelope/outbox record to durable local storage before attempting network send. A failed persistence transaction must not publish ciphertext or advance the active in-memory state.
- **Inbound:** authenticate/decrypt using a candidate state. Commit the candidate state, a unique processed-envelope/deduplication marker, and the locally protected inbox item in one durable transaction before acknowledging delivery or showing the message as committed. If the transaction fails, discard the candidate state and do not acknowledge the envelope.
- After a successful transaction, promote the candidate state to the active state.
- A separate `AtomicFile` for ratchet state cannot by itself make the ratchet update atomic with inbox/outbox records. The eventual Android persistence layer must provide the required transaction boundary (for example, a suitable encrypted local database or a journal protocol with equivalent crash guarantees) and test process death at every commit boundary.

These requirements are preconditions for connecting the ratchet to the Android chat UI or acknowledging network delivery.

## 7. Rollback limitation

AEAD authenticates a stored record but does **not** prevent an attacker or a device rollback from restoring an older, still-valid snapshot. An older sender state can rewind a chain counter and cause message-key reuse; an older receiver state can forget consumed skipped keys. Android's no-backup setting and atomic file replacement help with ordinary app operations but are not a cryptographic anti-rollback guarantee against a privileged attacker or full device rollback.

V1 rollback policy decision: REQUIRE ANTI-ROLLBACK PROTECTION (selected scope; recorded 2026-10-24; persistence design remains NOT FROZEN). The project owner selected the stronger policy: do not freeze this persistence format or claim production readiness until a suitable anti-rollback mechanism is designed, independently reviewed, and tested. The proposed catalog HMAC, record generations, per-session DEK wrapping, and ordinary atomic storage do not by themselves prevent restoration of an older, internally consistent full-device snapshot. The mechanism must define its trusted freshness anchor, threat-model coverage, platform availability and limitations, offline behavior, anchor-loss/recovery behavior, and fail-closed response when freshness cannot be established. Tests must restore a mutually consistent older snapshot and prove rollback is detected or use is blocked before any ratchet operation can reuse an old message key or forget a consumed receive key. A database generation stored in the same rollbackable snapshot is not an independent anti-rollback anchor. If a mechanism satisfying these requirements cannot be supported on target platforms, stop and return to the project owner for an explicit scope decision; do not silently downgrade to the narrower policy. Until the mechanism and tests are accepted, this design remains NOT FROZEN and the production release gate remains blocked. The format alone must never be described as rollback-proof.

Regardless of the selected scope, ordinary crash recovery must never select a torn or partially written record. Detected corruption, conflicting valid records, an ambiguous recovery state, or a failed transaction must fail closed rather than silently initialize a new ratchet session.

## 8. Required tests before the boundary is considered implemented

- Round-trip Alice-initial, Bob-initial, post-Message-0, normal-send/receive, DH-ratchet-transition, and non-empty skipped-key states.
- Continue a message exchange after restore and prove the restored sender does not repeat the prior message key and the receiver retains correct replay/out-of-order behavior.
- Persist and restore the maximum permitted skipped-key set; reject one beyond the limit and duplicate skipped-key IDs.
- Reject wrong storage key, changed session binding, corrupted header, corrupted nonce/ciphertext/tag, truncated/trailing data, unsupported version, non-canonical CBOR, unknown/missing fields, wrong field types/lengths, invalid `DHS_priv`/`DHS_pub` pairing, and invalid counters/state combinations.
- Confirm fresh random nonce per save and confirm sealed records do not contain raw key bytes as plaintext fields.
- Wrapped-DEK negative tests: wrong nonce/tag, modified header/version, wrong session/account/device binding or epoch, malformed record length, and missing Keystore alias must all fail closed without creating a new session.
- Catalog-authentication tests: modified entry/index payload or MAC; unknown catalog MAC-key version or schema version; non-canonical payload; requested session absent from the authenticated index; changed local identity, peer identity, or epoch; altered index ordering; substituted sealed-state or wrapped-DEK record; an old valid entry/state/wrapped-DEK set replayed against the current index must fail closed, and changing an entry key-version byte must change the entry commitment and fail MAC verification.
- Version-framing tests must prove the untrusted key-version byte selects only an allowlisted alias, is included in the MAC input, and is checked against supported authenticated schema fields after MAC verification; no fallback alias may be attempted.
- Generation/index tests must prove every successful state transaction updates the entry commitment and index MAC atomically, stale concurrent generations are rejected, and a failed transaction leaves state, index, entry, inbox/outbox, and acknowledgements unchanged.
- Catalog size-bound tests must encode the maximum 1,024-entry index below 256 KiB, reject entry 1,025 before mutation, and reject over-limit payloads before large allocations; revisit the cap if real product requirements demand more sessions.
- Epoch-freshness tests must reject or apply the explicitly documented policy to a session whose local epoch is stale after account rotation/recovery, and exercise peer-epoch change/revocation behavior without trusting epoch values solely from the catalog.
- Lifecycle/KT integration tests must prove that KT inclusion/current-state evidence does not substitute for account-epoch authorization, a forged or replayed epoch-transition result is rejected, the native verified account-state context supplies the epoch (not Kotlin), and offline restore follows only the documented cached VERIFIED/DEGRADED/SECURITY_FAILURE policy.
- Missing/invalid catalog MAC key with existing catalog data must fail closed without automatic key regeneration. Test first-time key creation only on explicit clean initialization, catalog-key rotation, and interrupted migration.
- Restore tests must prove index MAC validation precedes trusting session metadata, the entry binding matches the index, and record digests match exact stored bytes. Confirm UI/API paths cannot bypass the internal catalog-verification adapter and do not accept a boolean verification assertion as proof. Confirm tampering/substitution tests pass without claiming detection of a complete older valid snapshot or compromise of the app process.
- Verify the serialized wrapped-DEK record is exactly 69 bytes for V1, uses a fresh GCM nonce on each wrap, and contains no plaintext DEK bytes.
- Key-rotation tests must cover old-version restore during migration, successful rewrap, interrupted migration, and atomic recovery from either the old or new valid wrapped record; never require the old alias to be deleted before every dependent record has migrated.
- Verify failed decrypt/authentication and failed persistence do not commit state. Exercise duplicate envelopes and concurrent attempts.
- Android instrumentation: process restart restores the same session state; interruption during writes preserves either the prior committed state or the new committed state, never a partial record; missing storage key fails closed.
- Crash/fault-injection tests around the atomic inbox/outbox + state transaction. A successful round-trip test by itself is not sufficient.
- Maximum-size test: a state with 1,000 skipped keys must encode below the PM-CBOR 256 KiB whole-input limit; 1,001 keys must be rejected before encoding or use.
- Inject a durable-transaction failure after candidate encryption/decryption and verify the active state, outbox/inbox, and acknowledgement status remain unchanged.
